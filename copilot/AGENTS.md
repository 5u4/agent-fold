# AGENTS.md

Run every command here from `copilot/` unless a step says otherwise.

## Extension
`extension.ts` is a GitHub Copilot CLI extension. `bun run build` bundles it with `@github/copilot-sdk` left external into `com.github.copilot/extensions/agent-fold/extension.mjs`, which is committed because the CLI loads it from the plugin directory without a build step. `build.test.ts` fails when the committed file differs from a fresh build, so run `bun run build` after every source change. Extensions are an experimental Copilot CLI feature; every smoke run here used `--experimental`.

The extension registers through the SDK's private parent-process client with a `requestHandler`, because `joinSession` cannot take one. It joins with `additionalDirectories: [foldHome]` so the model can read and write the fold dir without a path prompt, and rewrites the outgoing `session.resume` to `requestPermission: false`. It supplies no permission handler. With `requestPermission: true` the CLI shows an elevation dialog at load, and `-p` without `--allow-all-tools` hangs when that is denied.

## Folding
The handler rewrites a request only when its URL path is in the `formats` registry (`/responses` and `/v1/messages`), `ctx.interactionType` is `conversation-agent`, the body has no content encoding, and the body holds at least one run boundary. Everything else, including title requests on `/chat/completions`, the frustration classifier, subagents and compaction, is forwarded as the original request object. Any error in the rewrite forwards the original request.

Each format classifies its native items as `boundary`, `steering`, `reply`, `drop`, or `keep`. A boundary is a user item with a text part that starts with `<current_datetime>` or with the compaction summary's "Some of the conversation history has been summarized". `fold.ts` folds every run except the last when the run's last `reply` or `drop` item is a `reply`. A folded run keeps its boundary, its steering and `keep` items, and its replies. On `/v1/messages`, kept items lose `thinking`, `redacted_thinking`, and `tool_result` blocks, and an item left with no blocks is dropped. Kept items are never converted into another format, so their ids, phases, and unknown fields pass through, and items outside folded runs pass through unchanged.

The handler appends `context/fold.md` to the system position (`instructions` or a leading system input item on `/responses`, `system` on `/v1/messages`) and inserts the `INDEX.md` snapshot right after the last boundary. The snapshot is read again only when the text of the last boundary changes, so it stays fixed for the whole run. It keeps at most 300 lines and 153600 bytes, like omp.

## Fold dir
The fold dir is `${AGENT_FOLD_HOME || ~/.agent-fold}/<project-slug>/copilot/<UTC start yyyymmddHHMMSS>-<session id>/`. `fold-dir.ts` reproduces omp's slug: the main checkout of the git repo holding the working directory, the checkout's top level when its git common dir is not a `.git` dir, or the working directory outside git. The working directory comes from `session.rpc.metadata.snapshot()` of the joined session. The start time and id come from the conversation root, so a fork and a fork of that fork share the original session's dir and `INDEX.md`, like omp, where a fork keeps the same key.

The SDK exposes no fork parent, so `session-root.ts` reads private CLI state. It reads the first line of `$COPILOT_HOME/session-state/<id>/events.jsonl` for every session dir. That line is the `session.start` event. A fork copies the parent's events, so its first event keeps the parent's event `id` and gets its own `data.sessionId` and `data.startTime`. The root is the session with the earliest `data.startTime` among those sharing the joined session's first event `id`. An ordinary session is its own root, and its `data.startTime` equals the snapshot start time, so its dir name is unchanged. If the original session was deleted, the earliest surviving fork is the root. In Copilot CLI 1.0.100 a fork's first line is on disk when its `session.foreground` arrives. A session created by `/new` or `/clear` has no `events.jsonl` yet when the owner joins it, so it has no root and uses the snapshot start time and its own id.

The extension creates the dir after it joins. A request waits at most 5 s for that setup and is forwarded unfolded if it is not done or if its `ctx.sessionId` was never joined. An error while resolving the root drops that session to unfolded requests.

## Session ownership
The LLM provider slot belongs to the CLI process, not to a session. The first extension process to call `llmInference.setProvider` owns it. The owner lives as long as its launch session stays open. It survives `/new`, `/fork`, and `/resume` from any session and `/clear` from any other session. `/clear` from the launch session closes that session through `sessions.close`, and the CLI stops the session's extensions. It sends the owner SIGTERM and force-kills it if it still runs 1 s later. `/exit` also sends the owner SIGTERM. The runtime sends a session's inference to the provider only after the provider joined that session, so the owner joins its launch session and every session named by a `session.foreground` lifecycle event. `FoldHandler.sessions` maps each joined session id to its fold setup, and the handler looks up `ctx.sessionId` there.

When the TUI switches back to a session, it replaces that session's additional directories within about 30 ms after `session.foreground`, so `/resume` to an already joined session drops the fold dir grant. The extension therefore checks the grant on every `session.custom_agents_updated` and `session.skills_loaded` event of a joined session, which the runtime emits right after that replacement, and adds the fold dir back with `permissions.paths.add` when it is missing. A re-grant on `session.foreground` lands before the replacement and is lost. An `onUserPromptSubmitted` hook is called when the user submits a prompt, but registering it made the CLI show an elevated-permissions dialog when the extension loaded.

Every later session starts its own extension process. Its `setProvider` is refused with "Cannot set LLM inference provider while sessions are active", because the owner already joined a session. The runtime refuses once any SDK connection has joined a session in the CLI process, and accepts `setProvider` while the TUI has sessions that no SDK connection joined. The process exits with code 0 before it joins anything. Its one-line reason goes to that extension's log in `~/.copilot/logs/process-*-<pid>.log`. Nothing shows in the TUI. Exit code 1 also shows nothing in the TUI but marks the extension a startup failure in that log.

TUI `--resume`, `--resume=<id>`, `-r`, and `--continue` first create a throwaway session, and its extension is killed about 90 ms after the target session is foregrounded. If it calls `setProvider`, a dead connection holds the slot for the rest of the CLI process. If it joins anything, the target is refused and turns can hang. `launch.ts` therefore classifies the launch before any client exists. The launch is a throwaway when the parent CLI's argv has one of those flags, `$COPILOT_HOME/session-state/<SESSION_ID>/events.jsonl` does not exist, and another session dir has an `events.jsonl`. A throwaway exits at once, and the target session's extension becomes the owner without the 30 s wait for extensions. A session created later by `/new` in such a CLI also matches the rule and exits early, which is harmless because the owner joins it. Bare `--resume` that opens no picker stays in its new launch session, matches the rule, and runs unfolded. The argv comes from `ps`, so on Windows it is never read and the rule never fires.

Once `setProvider` succeeds the owner never exits on its own. Copilot CLI 1.0.100 has no call that frees the provider slot, so after the owner dies a dead connection holds it. Every later `setProvider` is refused, with "Cannot set LLM inference provider while sessions are active" while a session the dead owner joined is still loaded and with "Another client is already the LLM inference provider" otherwise, and nothing folds for the rest of the CLI process. A loaded session that the dead owner joined, or was joining when it died, sends every request to the dead connection, the CLI logs `llmInference drain: outbound request failed to send ... UnknownConnection(<id>)`, and the turn stays on "Working". A session the owner never joined answers unfolded.

The extension therefore keeps the dead owner's joined sessions out of reach. `/new`, `/resume`, and `/clear` all send `session.background` for the session the TUI leaves and then `session.foreground` for the next one, and `/clear` closed the session it left 58 to 81 ms after that `session.foreground` in seven smoke runs. The owner cannot tell them apart, so when the TUI leaves the launch session it waits 1 s before it joins the next session. If that switch was a `/clear`, the owner is dead before the join and the cleared session answers unfolded. In one smoke run a prompt typed 0.25 s after `/new` sent its first `/v1/messages` request 1.46 s after `session.foreground`, after the join, and it was folded. On SIGTERM the owner detaches every session it joined with `session.detach`. A background session that only the owner held then closes, and a later `/resume` loads it again and answers unfolded. A detach does not unbind a session the TUI still holds. When the owner joined the cleared session during its shutdown and then detached it, the next turn still hung, which is why the join waits. A join or setup error only drops that session to unfolded requests, and any error in a request forwards the original.

## Verify
- Run `bun run typecheck` and `bun test`; `bun test` includes the rebuild check. From the repo root, run `biome check copilot`.
- Smoke every behavior change in a scratch git repo with a copy of the build at `.github/extensions/agent-fold/extension.mjs`, `AGENT_FOLD_HOME` set to a temp dir, and the TUI in tmux. Answer folder trust with the one-time "1. Yes". To see what reaches the model, patch a copy of the build to write each request's body before and after the rewrite; never commit that patch.
  1. On one Claude model (`/v1/messages`) and one GPT model (`/responses`), such as `claude-haiku-4.5` and `gpt-6.1-sol`, run "Use a shell command to cat data.txt, then reply with only the word done", then "Without using any tools, what exact token was in data.txt?". With the extension the second answer does not quote the token and the token is absent from the second request. In a scratch repo without the extension the model quotes it. `claude-sonnet-5` answered `UNKNOWN` even without the extension, so it cannot be the Claude model for this check. Copilot CLI 1.0.100 rejected `--model gpt-5.4-mini` and fell back to `gpt-6.1-sol`.
  2. Ask the model to append a line to the session index under `--allow-all-tools`. No dialog appears, and the next run's request carries the line right after its boundary.
  3. In one TUI, run `/new`, `/clear`, `/fork`, and `/resume <earlier id>`, each followed by the check in step 1. The check's turn requests are logged under the active session's id and folded. `/new` and `/clear` get their own fold dir. `/fork`, and `/fork` again from the fork, reuse the original session's fold dir: the request's rules name it, the request carries the line step 2 appended to its `INDEX.md`, and no new dir appears. Quit and start the TUI with `--resume <fork id>`: still the original dir. If the first turn's reply quotes the token, the second request still sends it, because folding keeps replies.
  4. After `/resume` back to an earlier session, the next request lists the fold dir under "Additional directories available for file access" and carries no `<additional_directories_changed>` notice. Then, without `--allow-all-tools`, ask the model to append a line to the session index. The only dialog is the usual command or edit approval, and none asks about the fold dir path.
  5. Quit, then start the TUI with `--resume <id>`, `--resume=<prefix>`, and `--continue` in turn. Startup does not stall for 30 s, the turn answers, and its request is folded under the target session id. Then `/new` and a turn: folded by the same owner.
  6. Run `copilot --session-id <new uuid>`: the check in step 1 folds.
  7. Run `copilot -p` with `GITHUB_COPILOT_PROMPT_MODE_EXTENSIONS=true` and without `--allow-all-tools`, then the same with `--continue`. Both answer and exit, and both requests are folded.
  8. Start the TUI plain, and again with `--resume <id>`. In the launch session run a turn, then `/new` and a turn, `/resume <launch id>` and a turn, and `/clear` and a turn. The owner's extension log ends with `exit code=0 disposition=stopped-normally`, and the turn after `/clear` answers unfolded in a few seconds. Then `/resume` to the `/new` session and a turn, and `/resume <launch id>` and a turn: both answer unfolded. The CLI log has no `UnknownConnection` line.
